### 2026-08-09 — Retrospective "value" framing fix + position breakdown (commit `bf6ecf6`)
- Arjun: Josh Allen was drafted R3 specifically to lock in a top QB before someone else did — the retrospective calling him "best value" purely for having the highest points-per-week rate was conceptually wrong. Value means a *late* pick outproducing its slot (low opportunity cost); an early premium-position pick performing well is expected, not value.
- Fix in `_narrate()`: every pick line is now tagged `(early-round pick)` / `(late-round pick)`, split at `max_round / 2` computed from the actual picks. The system prompt only permits "value" framing for late-round-tagged picks; early picks that performed well get "justified early investment" instead, with the LLM asked to discuss whether the *opportunity cost* (draft capital spent there vs. elsewhere) paid off — not just whether the player was good.
- New `_position_breakdown()`: groups picks by `player.position` (real position — QB/RB/WR/TE/etc., not lineup slot), aggregates total points and points-per-started-week rate per group, appended to the prompt as its own section. Directly answers Arjun's ask for "points normalized for each position."
- Confirmed live (`data/retrospective_2025.json` regenerated again — third regen this session): Allen now reads as "best early-round investment... fully justified the third-round draft capital," Courtland Sutton (R7) is named the genuine value pick, and the position breakdown surfaced that the RB group (11.6 pts/started-week across 4 picks) underperformed relative to the early draft capital spent there, vs. QB at 25.8 on a single pick — a real, usable roster-construction signal.
- Note: "Flex" wasn't broken out as its own group — flex is a *lineup slot* a player gets started in some weeks, not a draft/real position, so grouping by `player.position` (their actual position) is the meaningful axis for "did I get good return at RB vs WR," not flex-slot usage. Didn't build separate flex-slot-usage reporting; revisit only if Arjun specifically asks for that distinct thing.

### 2026-08-09 — Weekly performance breakdown, fixes a real retrospective bug (commit `c88a85a`)
- Arjun tested the deployed retrospective himself and caught it: Davante Adams showed as a 0-point "bust" despite being a full-season starter, and CeeDee Lamb's injury weeks (benched 3–6, per box scores — though ESPN's `injuryStatus` field stayed "ACTIVE" throughout in this historical data, doesn't reliably reflect real injury designations retroactively) weren't visible anywhere.

Anyone since moved off the roster is invisible to the roster pull entirely — the earlier "0 pts, blank position for traded/dropped players" caveat was actually a real, systemic bug, not a rare edge case.
- Fix: `app/models/league.py` adds `WeeklyPerformance` (week, points, slot) and `Player.weekly: list[WeeklyPerformance]`. `app/adapters/espn.py`'s new `_enrich_with_weekly_performance()` walks `league.box_scores(week)` for every regular-season week (`settings.reg_season_count`, 14 for this league — not 17, corrects an assumption Arjun stated) for the *requesting user's own team only* (not all 12 teams — scope matches what the retrospective actually needs), attaching weekly points/slot to every player who ever appeared in that team's weekly lineup, including ones no longer on the current roster. Also backfills name/position/pro_team for those recovered players directly from the box-score entry (`BoxPlayer` carries its own `name`/`position`/`proTeam`), which incidentally also improves draft-pick accuracy for departed players beyond just the points question.
- Second, subtler fix in the same commit: `total_points` was being read from the live player object's whole-*season* stat, which reflects real NFL production regardless of which fantasy roster the player ended up on — not what they scored specifically *on this team*. For anyone who changed fantasy rosters mid-season these differ a lot. Verified live: Zach Charbonnet was credited as the original retrospective's "best-value" pick at a season-long 161.4 points, but was only actually on Shiznits' roster 3 of 14 weeks (11.7 pts) — the rest of his production happened on whatever roster picked him up after. `total_points` is now recomputed as the sum of `weekly` wherever weekly data exists, so it's roster-specific everywhere it's shown.
- `app/services/retrospective_service.py`'s prompt now shows weeks-on-roster, weeks-started (excludes `BE`/`IR` slots), roster-specific total, and points-per-started-week rate per pick — and instructs the LLM to judge value primarily by rate + weeks-started coverage rather than a raw total (so a full-season starter and a 3-week rental with a similar total read as very different outcomes, and a 1-2 week hot streak doesn't get over-credited as "proven value"). Picks with zero weeks on the roster are flagged as genuinely unknown production, not guessed at.
- Deleted the stale `data/retrospective_2025.json` (computed before this fix, from the caching change earlier this session) and re-synced 2025 + regenerated live via the running server — confirmed the new fields and reasoning are correct before handing back to Arjun to review in the browser himself.
- Residual known gap: a pick with weekly data missing (never appeared in any weekly lineup, e.g. Stefon Diggs in this league — likely cut before Week 1, or re-added to the current roster from an unrelated later move) still carries whatever `total_points` the live player object reports, which can be a stale/unrelated real-NFL stat. The retrospective prompt handles this by treating zero-weekly-data picks as explicitly unknown rather than trusting that total — but the underlying `Player.total_points` field itself isn't corrected to 0 or null in this case, only the prompt's interpretation of it.
